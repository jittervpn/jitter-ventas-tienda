What an SSH tunnel over WebSocket is and what it's for

Updated on November 24, 2026, by the Jitterx Panel Cloud team

An SSH tunnel over WebSocket is a way to send your internet traffic through a remote server, encrypted end to end up to that server, over a connection that looks like normal web traffic. It's widely used by developers, system administrators and people who want an extra layer of privacy. This guide explains each piece calmly.

First: what SSH is

SSH (Secure Shell) is a protocol built to manage servers securely. Everything sent over an SSH connection is encrypted, and the server identifies you with a username and password or a key. Besides opening a remote terminal, SSH can create tunnels (port forwarding): the server acts as a middleman and forwards your apps' traffic to its final destination.

A typical case is dynamic forwarding (ssh -D), which turns the server into a SOCKS proxy. Apps that use that proxy send their data through the encrypted tunnel and reach the internet with the server's IP address, not your local network's.

What WebSocket adds

WebSocket is a web standard that starts as a normal HTTP request with an Upgrade: websocket header and, if the server accepts, keeps the channel open to exchange data both ways. It's used in chats, online games and real-time dashboards.

Wrapping SSH inside WebSocket means the connection starts with an HTTP handshake and then carries the SSH stream. The practical advantage is that it travels over ports 80 and 443, which almost every network leaves open, and it works well with web proxies and content delivery networks (CDNs). On office, university or venue networks with restrictions, direct SSH (port 22) is often blocked while web traffic isn't.

How it works end to end

  1. A client app (for example HTTP Custom or NetMod on Android) opens an HTTP connection to the server.
  2. It sends the WebSocket upgrade request; the server answers with code 101 (Switching Protocols).
  3. The SSH session is negotiated over that channel and your user is authenticated.
  4. The app exposes a local proxy or VPN on the phone; your apps' traffic goes in there, travels encrypted to the server and leaves from there to its destination.

Common legitimate uses

  • Privacy on networks you don't control: cafés, airports or hotel WiFi.
  • Access to your own resources: reaching internal services on your VPS or at home without exposing them to the internet.
  • Development testing: checking how a website or API behaves from another location.
  • Over-filtered environments: networks that block ports indiscriminately.

Limits and precautions

  • You trust the server operator. The tunnel protects you between your phone and the server, but the operator can see which destinations you connect to. Choose providers you trust.
  • It doesn't replace HTTPS. Secure websites still encrypt their content inside the tunnel, and that's what protects your passwords.
  • It doesn't protect you from phishing or malware. A tunnel encrypts the route; it doesn't decide whether the site you visit is legitimate.
  • It can add latency. Each extra hop adds milliseconds; speed depends on the distance to the server and its load.

Responsible use. Use these techniques in line with your country's laws and the rules of the networks and services you use. A tunnel is a privacy and administration tool, not a license for abuse.

Why it fits a CDN

Because the connection starts as a normal web request, a CDN like CloudFront can receive it on its network and forward it to your server. Your app connects to the CDN's domain and the tunnel reaches your VPS.
